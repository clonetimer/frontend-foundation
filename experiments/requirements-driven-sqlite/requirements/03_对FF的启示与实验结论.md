# 需求驱动实验：阶段结论（不合并 FF）

## 观察

一句很短的业务需求，产生了至少十四条需要判断的设计问题。最影响架构的不是按钮颜色，而是 Q-02（数据库文件是什么）、Q-03（多次导入如何处理）、Q-04（查询语言）、Q-05（导出范围）、Q-10（运行权限与部署）。

本实验在**不要求用户先理解数据库建模和 API**的前提下，为这些问题提出了透明、可回滚的默认选择，并构建有真实持久化的闭环。这是从客户业务语言走向实现所需的“需求理解层”一个可操作实例。

## 与已有 FF 能力的边界

| 环节 | 已有 FF 技术能力可复用 | 本实验新增的非 FF 价值 |
|---|---|---|
| 上传与校验 UI | 表单/弹窗/错误提示/布局组件 | 必答/可选问题和格式异常策略确认 |
| 数据列表和查询 | DataTable、远程数据、分页/筛选交互 | 查询运算符、结果完整性、数据类型的业务决策 |
| 下载与交付 | 前端下载交互与独立前端源码输出 | 明确 SQLite 是服务端生成的业务数据文件而非前端组件文件 |
| 错误场景 | 已有异步/不确定操作防护 | 逐条可追踪验收证据及未测边界 |
| 业务部署 | FF 只负责前端项目能力 | 本地解析与数据库由独立 Python 服务完成，不能混淆 |

## 决策建议（研究建议，未经业务方批准）

优先研究并验证 **需求采集/追问模板与验收用例生成**，先作为 FF 外部流程，不立即扩大 Studio DSL、引入 LLM 内核或自动生成后端。

可探索的产物格式不是巨大的 Word，而是一个版本化的需求包：`原始业务描述 + 未决事项 + 决策记录 + 页面草图 + API 契约 + 验收追踪表`。使用已有 Studio 画布完成界面，再用真实后端接口履约。

若未来要使用 LLM 做需求追问，应强制保留事实来源和置信标记：`用户明确`、`需求文档直接支持`、`模型建议待确认`、`开发实现假设`，不可以把模型建议偷偷转成硬性需求。

## 已知缺口

本实验没有通过真实浏览器 HTTP 联调门禁（执行环境禁止 Chromium 连接本机 HTTP）；虽然 HTTP API 和静态语法检查已通过，实际页面交互体验需要用户本机验收。未支持 XLSX、多数据库关联、生产权限/审计、超大文件流式导入、复杂时间类型、正式业务数据质量策略。不提供任意 SQL 查询，也不负责数据库长期治理。

因此研究阶段的结论为：**业务闭环的独立本地后端具备可验证的实现；需求追踪方法可以运行；FF Studio 集成与严格对照实验待后续验证。**
