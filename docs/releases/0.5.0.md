# Frontend Foundation 0.5.0

Status: **Stable Readiness Candidate**

## Summary

- Freeze the dependency graph with a committed `pnpm-lock.yaml`.
- Add two domain-neutral regression Pilots: management and data-workbench.
- Add named public-API snapshot verification for every publishable TypeScript Foundation package.
- Add `foundation-upgrade` dry-run/write workflow to align Foundation package versions without rewriting source.
- Harden tarball packaging with declared import/type artifact checks and a 100 KiB Foundation library-entry budget.
- Add per-tarball `sizeBytes` + SHA-256 integrity metadata and verify it again before registry publication.
- Validate packed 0.5.0 Foundation tarballs in independent Browser- and Hash-router applications using the Linux offline dependency snapshot.
- Harden API cancellation/timeout races, Async polling deadlines, ECharts theme reinitialization, and Windows/standalone-pnpm tooling behavior without expanding Kernel public contracts.

## Compatibility

- Kernel public contract: no intentional breaking public-contract change from the 0.4.x line.
- Named public package exports: frozen by `tooling/release/public-api.snapshot.json`.
- Migration requirement: applications must align all `@foundation/*` packages to the 0.5.x minor line.
- Recommended migration sequence:

```bash
foundation-upgrade . --target 0.5.0
foundation-upgrade . --target 0.5.0 --write
foundation-doctor . --target 0.5.0 --strict
```

Then regenerate the application lockfile intentionally and run its own typecheck/tests/production build.

## Remaining promotion gates

These require infrastructure that is intentionally external to the source repository:

- [ ] clean `pnpm install --frozen-lockfile` against the target connected/mirrored package source (the cloud environment has no registry connectivity; validation used the uploaded dependency snapshot instead);
- [ ] candidate publication to the actual private registry and clean install from that candidate dist-tag;
- [ ] manual browser smoke for navigation, theme switch and Browser/Hash history behavior in a supported deployment;
- [ ] at least one real application upgrade using the documented 0.4.x → 0.5.x procedure before any 1.0 Stable decision.

0.5.0 therefore remains a **Candidate**, not a Stable/`latest` release.
