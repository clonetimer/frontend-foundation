# Frontend Foundation 0.20.0

Status: Candidate

## Summary

0.20 turns the 0.19 Custom Registry contract into an engineering SDK for project-owned domain components while keeping all project-specific implementations outside the Foundation Runtime Kernel.

- Added `foundation-domain init / verify / merge` to `@foundation/create-app`.
- Domain package admission validates package identity, Registry/package version compatibility, explicit source exports, actual built ESM exports and `npm pack` contents.
- Added a retained private, domain-neutral `@example/domain-widgets` regression fixture with `InteractiveViewer`, `TimeSeriesChart` and child-accepting `AnalysisSection`.
- Storybook renders the real fixture components while the Visual Designer continues to use safe metadata-only placeholders/containers.
- Designer regression consumes the same Registry to verify Palette/Property/Binding/Event/container metadata integration.
- Added a domain-neutrality governance gate that prevents concrete product-domain vocabulary from entering Foundation Runtime, Designer or Compiler mainline sources.
- Custom Registry tests are now part of the dependency-independent clean-ZIP offline gate.
- Release governance requires the Domain SDK fixture, lockfile importer, Storybook dependency and `foundation-domain` packed binary.
- Runtime Kernel source remains unchanged from the reviewed 0.19 baseline.

## Compatibility

- Project Blueprint v1 and Custom Registry v1 remain compatible and additive.
- Existing 0.19 projects do not need a migration unless they choose to adopt the package engineering workflow.
- `foundation.registry.json` remains the project/compiler contract; the SDK does not add a runtime plugin model.
- Owned Runtime Kernel baseline remains the reviewed 0.19 / 62-file baseline.
- The retained SDK fixture is explicitly test-only and outside `@foundation/*`; it is not a product/domain dependency of Frontend Foundation.
